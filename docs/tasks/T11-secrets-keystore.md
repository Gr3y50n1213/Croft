# T11: Secrets and the Android Keystore

Crate / folder: `core/ffi` (SQLCipher feature wiring only) + `android/` (keystore code, package `com.example.croft.secrets`)

Depends on: T01 (`Db::open` with a key, feature `sqlcipher`), T10 (the `Core.open` signature and the `CredentialProvider` callback, both built). Blocks: T17 (sign-in), T21 (OAuth tokens).

**Status: built on branch `task/t11`, then changed after two security reviews (see "Security review fixes" and "Second round" at the end, which win where they differ).** The spec below is what was built first; "As built" at the end lists the differences from the first version of this file and what could not be checked here.

## Goal
Passwords, OAuth tokens and the database key live only in the Android Keystore. They never reach SQLite, config files, logs or crash reports, and the Rust core never stores a secret.

## Spec
- **Database key.** On first run generate 32 random bytes, wrap them with a non-exportable AES-256-GCM key in the Android Keystore (`AndroidKeyStore`, StrongBox when available, else TEE), and keep only the wrapped blob in app-private storage (`noBackupFilesDir/croft-secrets/db-key.v1`). At start the app unwraps it and passes it to `Core.open` (`openCore` in `RustBridge.kt`), then wipes its copy. The cipher sits behind a small `SecretBox` interface (`seal(plain, context)` / `open(blob, context)`); the one implementation, `AesGcmSecretBox`, takes its key from a `WrappingKeySource` (the Keystore on a phone, an in-memory JCE key in tests), so the envelope format and every failure path run on the JVM.
- **Envelope.** `version byte (1) | 12-byte IV | ciphertext | 16-byte GCM tag`. The IV is chosen by the cipher (the Keystore requires it). The additional authenticated data is the version byte followed by the *context* (`croft/db-key/v1`, or `croft/secret/v1/<account id>/<kind>`), so a blob copied onto another entry, or with a changed version byte, does not open (the version byte was added to the AAD after the review; no blob had been released, so version 1 changed in place).
- **SQLCipher in the Android library.** The Android library and the host library the JVM tests load are built with the cargo feature `sqlcipher-vendored-openssl` of `croft-ffi` (`rusqlite/bundled-sqlcipher-vendored-openssl`: SQLCipher plus OpenSSL's crypto compiled from source with `openssl-src`; the NDK has no OpenSSL to link). `croft-ffi` also has the plain feature `sqlcipher` (host OpenSSL, used for `cargo test -p croft-ffi --features sqlcipher`). The app always passes a key: a library built without the feature refuses it (`StorageReason::EncryptionUnavailable`), so a lost feature fails at open and never stores mail unencrypted.
- **Account secrets.** `SecretStore` keeps one entry per `(account_id, kind)` (`PASSWORD`, `OAUTH_REFRESH`, `OAUTH_ACCESS`) as one wrapped file in the same folder. `remove` and `removeAccount` delete files; the app calls `removeAccount` **before** `Core.removeAccount` (see "Security review fixes"). Secrets go in and out as `ByteArray`; `put` copies and the caller wipes (`fill(0)`); the array `get` returns is the caller's to wipe. A damaged entry or one made for another entry reads as `null` and is deleted (the person signs in again). A keystore failure is an exception (`KEY_LOST` or `UNAVAILABLE`) and deletes nothing.
- **Credential callback (T10's, not redefined).** `SecretStoreCredentials` implements `uniffi.croft_ffi.CredentialProvider`: `credential(accountId)` reads the store and returns `FfiCredential.password(bytes)` (or `FfiCredential.oauth2(user, bytes)` when an access token is stored and the `userFor` lookup knows the account name), then wipes its array; any store failure reads as `null`. The core then calls `signInNeeded(accountId)`, which adds the id to `SignInNeeded.accounts` (a `StateFlow<Set<Long>>`) for the screens; the person fixing it calls `SignInNeeded.clear` and `Core.signedIn`. For an account being added, the credential is an argument of `Core.addAccount` (API version 4) and `AccountSecrets.addPasswordAccount` stores it under the returned id; the provider is never asked about a new account (`withStagedPassword` was removed, see "Security review fixes"). The engine's rules are unchanged: it calls the provider when an adapter is built, never from the UI path, and a missing credential is `BackendError::Auth` (the account pauses as Needs sign-in; it is not counted as a transient failure).
- **Never logged.** Every Kotlin class that holds or handles a secret overrides `toString()` to `[redacted]` (`DatabaseKey`, `SecretStore`, `AppSecrets`, `AesGcmSecretBox`, `KeystoreKeySource`, `SecretStoreCredentials`, `SignInNeeded`, `KeyLossNotice`); `SecretBoxException` carries only a fixed kind, no cause and no text; no class is `Serializable`. On the Rust side `FfiCredential` is an object whose `Debug` prints `***` (T10).
- **Backups.** `allowBackup="false"` and the extraction rules stay; `BackupRulesTest` passes. The encrypted database cannot be allowed to back up later: the key is bound to this device's Keystore and the wrapped blob is useless elsewhere.
- **Key loss.** (First version; the rules are tightened in "Security review fixes".) `AppSecrets.databaseKey()` resets when the wrapping key is definitely gone: the wrapped file cannot be opened (`KEY_LOST` or `CORRUPT`), or data exists without it. It then moves the database (and `-wal`, `-shm`, `-journal`), every account secret and the wrapped key file into a quarantine folder, makes a new key, and raises `KeyLossNotice.pending` (a `StateFlow<Boolean>` backed by a marker file, so it survives a process kill; the first screen shows plain text and calls `acknowledge()`; a later task draws it). Mail is re-synced from the server. A Keystore that merely fails (`UNAVAILABLE`: busy, restarting) is retried and then reported; nothing is moved or deleted.

## Done when
- Rust: `Db::open` with the key opens an encrypted file; with a wrong key returns the existing wrong-key error and leaves the file unchanged; a plain-SQLite reader cannot read it (`cargo test -p croft-storage --features sqlcipher`; the same through `Core::open`: `cargo test -p croft-ffi --features sqlcipher`, `core/ffi/src/tests/encrypted.rs`).

- JVM, host library (T10 surface): the provider hands a stored password to the core on add and on reopen; a missing secret leads to Needs sign-in and the account is marked; signing in again resumes it (`SecretStoreCredentialsTest`); the database key goes through `openCore` into a real encrypted file (`OpenCoreTest`).
- Grep-style test: no secret type is `Serialize`, and no table or column in `core/storage/migrations/` is named for a password or token (`NoSecretsInSourcesTest`); every secret-holding Kotlin class prints `[redacted]` and never the fixture secret (`SecretPrintingTest`).
- Real Keystore class: `KeystoreWiringTest` (what Robolectric can run; see "As built").
- On a device (not checkable here): StrongBox availability, key survival across a reboot and across a screen-lock change, behaviour after "clear data". Reported as unverified.

## As built

Code: `android/app/src/main/kotlin/com/example/croft/secrets/` (`SecretBox.kt`, `KeystoreKeySource.kt`, `SecretStore.kt`, `AppSecrets.kt`, `SecretStoreCredentials.kt`), `openCore` in `RustBridge.kt`, features in `core/ffi/Cargo.toml`, `rustFeatures` in `android/app/build.gradle.kts`. Tests: `android/app/src/test/kotlin/com/example/croft/secrets/`, `core/ffi/src/tests/encrypted.rs`.

Differences from the first version of this file, and why:
- **No new callback surface.** The first version asked for a `Credential` enum and `credential_rejected`; T10 had already built `CredentialProvider` with `FfiCredential` (an object, so it cannot print a secret) and `sign_in_needed`. (The review later changed `add_account`: `FFI_API_VERSION` is now 4.)
- **SQLCipher is wired in `core/ffi`, not changed in `core/storage`.** `croft-ffi` got two features: `sqlcipher` (`croft-storage/sqlcipher`, host OpenSSL) and `sqlcipher-vendored-openssl` (adds rusqlite's `bundled-sqlcipher-vendored-openssl`). `core/Cargo.lock` gained `openssl-sys` 0.9.118 and `openssl-src` 300.6.1+3.6.3 (OpenSSL 3.6.3, Apache-2.0).
- **Cross-compiles for both ABIs.** `cargo ndk -t arm64-v8a -t x86_64 --platform 26 build --release -p croft-ffi --features sqlcipher-vendored-openssl` succeeds (about 8.5 minutes from cold, 2 x 16 MB). Both libraries have every LOAD segment aligned 0x4000 (`tools/check-16kb-alignment.sh`). It needs `perl` and `make` on the build computer (the `openssl-src` build); CI's Ubuntu image has both.
- **The host library for the JVM tests is built with the same feature**, so the Kotlin tests open a real encrypted file through `openCore`. (`buildRustHost` and the bindings generator share `rustFeatures`.)
- **`MainActivity` is not changed.** It does not open the core yet; T12 and later screens call `createAppSecrets(context, dbFile)` and `openCore(...)`.
- **The OAuth user name is not a secret and is not in `SecretStore`.** `SecretStoreCredentials` takes a `userFor(accountId)` lookup; T21 decides where the name is kept.
- **A damaged account-secret entry is deleted and reads as null; a keystore failure is not.** `KEY_LOST`, `UNAVAILABLE` and `UNSUPPORTED_VERSION` on a secret read delete nothing. Only the database key's path moves everything aside, and only on `KEY_LOST`/`CORRUPT`, never on `UNAVAILABLE` or `UNSUPPORTED_VERSION`.
- **A core that refuses a valid key (`StorageReason.NOT_A_DATABASE`) is not treated as key loss** (the blob decrypted, so the Keystore is fine; the file is damaged). The caller decides; nothing is deleted automatically.

Not checked here:
- **Robolectric tests (`KeystoreWiringTest`, `HelloScreenTest`) did not run**: Maven Central answered 429 (retry after about 20 hours) for the 159 MB `org.robolectric:nativeruntime-dist-compat:1.0.19` jar, so `:app:testDebugUnitTest` could not resolve its classpath. Everything else was run directly with JUnit on the compiled classes and the host library (65 tests, `BackupRulesTest` included, all passing). `KeystoreWiringTest` is written to skip, not fail, when Robolectric's `AndroidKeyStore` cannot make a key; what Robolectric can do was therefore not confirmed.
- On a device: StrongBox, key survival across a reboot and a screen-lock change, "clear data", whether a lock-screen reset makes the key unusable on a given vendor's keystore (the `KEY_LOST` mapping rests on `InvalidKeyException`/`UnrecoverableKeyException` from the platform docs).
- (Done after the review: the `sqlcipher` job in `.github/workflows/ci.yml` now also runs `cargo test --locked -p croft-ffi --features sqlcipher`. Not run in CI yet, since this branch is unpushed.)

## Security review fixes (version 4 of the FFI)
A security review of the first version found the problems below; each is fixed on `task/t11`.

1. **A temporary Keystore error could wipe all data.** AOSP reports many transient failures as `UnrecoverableKeyException`, a plain `InvalidKeyException` or `IllegalBlockSizeException`, and on Android 8 to 11 a failed service connection makes `getKey` return null; all of those used to read as a lost key. Now (`KeystoreErrors.kt`, `KeystoreKeySource.kt`, `SecretBox.kt`, `AppSecrets.kt`):
   - `KEY_LOST` only on definite evidence: a `KeyPermanentlyInvalidatedException` anywhere in the cause chain; on API 33+ a non-transient `android.security.KeyStoreException` with a key-specific code (`ERROR_KEY_DOES_NOT_EXIST`, `ERROR_KEY_CORRUPTED`); or the alias missing from `KeyStore.aliases()` on 3 tries in a row (waits of 100 ms and 500 ms between them) while `aliases()` itself works. A key is also never created while its absence is unconfirmed (that would overwrite a key that is only temporarily unreachable); the second round tightens this (item 1: canary, persistence, no key over wrapped files).
   - `CORRUPT` only for `AEADBadTagException` and the envelope's own length and version-0 checks. `UNSUPPORTED_VERSION` for a version byte above 1.
   - Everything else is `UNAVAILABLE`: `AppSecrets` retries with backoff (100 ms, 500 ms, 2 s) and then throws `SecureStorageException(NOT_READY)` ("Secure storage is not ready; try again"); nothing is moved or deleted. `UNSUPPORTED_VERSION` throws `SecureStorageException(NEWER_DATA)` ("This data was written by a newer Croft") and never resets. A quarantine move that fails throws `STORAGE_ERROR`.
   - **The reset is reversible.** On definite key loss the database files, the wrapped account secrets and the wrapped key are moved (not deleted) to `noBackupFilesDir/croft-quarantine/<timestamp>/{database,secrets,key}/` (`Quarantine.kt`). The Keystore alias is kept (`discard()` is no longer called on a loss); it is replaced only when sealing the new key shows the entry is itself the dead key. Quarantined data is deleted after 7 days *and* at least 3 later successful starts (one per process; the start that made the incident does not count). Restoring was a support step in the first round; the second round restores by itself or offers it (see "Second round", item 2).
   - Tests: `KeystoreErrorsTest` (a fake for each exception type, the API 33 gate, cause chains, the JCE cipher failing through `FailingKey`), `KeystoreKeySourceTest` (the three checks and their delays, a transient null that is still listed, mixed answers, never generating over an unsure key), `SecretBoxTest.aHigherVersionIsUnsupportedNotCorruptAndNotAReset`, `AppSecretsTest` (`aLostKeystoreKeyMovesTheDatabaseAndTheSecretsAside...`, `eachKindOfFailureHasItsOwnOutcome`, `aBusyKeystoreIsRetriedWithBackoffThenFailsNotReadyAndNothingChanges`, `aKeyFromANewerCroftFailsAsNewerDataAndNothingChanges`, `aWrongCallCanBeUndoneFromTheQuarantine` (replaced in the second round by the automatic restore tests), `quarantinedDataIsDeletedOnlyAfterSevenDaysAndThreeLaterStarts`).
2. **A new account's password could go to another account's server.** `withStagedPassword` / `adoptStaged` handed the staged password to any account with no stored password. Removed. `Core.add_account` now takes the credential (FFI API version 4; see T10, "As built"); `AccountSecrets.addPasswordAccount` stores it under the returned id after the call and stores nothing if the call fails (and removes the account again if storing fails). `SecretStoreCredentials` answers only for stored accounts. Tests: `SecretStoreCredentialsTest.aNewAccountNeverGetsAnotherAccountsPasswordOrTheOtherWayAround`, `ifAddAccountFailsNothingIsStored`, `ifTheSecretCannotBeStoredTheAccountIsNotKept`; Rust `a_new_account_uses_the_credential_it_was_given_not_the_providers`.
3. **Account ids were reused** (SQLite rowids shrink when the last row goes), so a new account could find an old account's secrets. `core/storage/src/accounts.rs::insert` keeps the high-water mark in `setting` (`account.max_id`) and inserts with id = max(mark, MAX(id)) + 1 in one savepoint; no migration. On the Android side `AccountSecrets.removeAccount` deletes the secrets *before* `Core.removeAccount` (a crash in between leaves an account that needs a sign-in), and `SecretStore.putForNewAccount` clears every entry under the id before storing. Tests: Rust `accounts::tests::an_account_id_is_never_reused` (add 2, remove the second, add again gives 3), `a_removed_accounts_id_is_not_given_to_the_next_account` (through `Core`); Kotlin `anIdIsNeverReusedAndALeftoverUnderTheNewIdIsCleared`, `removingAnAccountDeletesItsSecretsBeforeTheCoreIsTold`, `SecretStoreTest.putForNewAccountClearsEveryEntryUnderTheIdFirst`.
4. **An unknown envelope version triggered the full reset.** It is now `UNSUPPORTED_VERSION` and never resets (see 1).
5. **Two `AppSecrets` instances could race on the first run.** `createAppSecrets` returns one instance per folder per process (`ProcessSecrets`), and `databaseKey()` runs under a process-wide monitor and a `FileChannel` lock on `croft-secrets/lock`. Tests: `twoInstancesRacingOnTheFirstRunMakeOneKey` (fails without the lock), `theProcessHoldsOneInstancePerFolder`. The cross-process half of the lock (a second process) is not tested.
6. **The parent directory is synced after the atomic rename** (`writeAtomically`, so for `SecretStore` and the wrapped key) and after quarantine moves; an `IOException` from the directory sync is ignored, the file's own sync is not. Test: `SecretStoreTest.writingSyncsTheDirectoryAndToleratesOneThatCannotBeSynced` (that the sync is not skipped is not observable from a test).
7. **The version byte is in the AAD.** Version 1 changed in place (no blob had been released); commented at `AesGcmSecretBox`. Test: `SecretBoxTest.theVersionByteIsPartOfTheAuthenticatedData`.

Also done: the CI `sqlcipher` job runs the `croft-ffi` tests, `android/README.md` documents the Rust features and the perl/make requirement, and `LICENSES.md` lists OpenSSL (Apache-2.0) and SQLCipher (BSD-style).

Known limits: a key entry that is permanently unusable but reports only a generic `UnrecoverableKeyException` (not `KeyPermanentlyInvalidatedException`, and no API 33 key-specific code) now stays `NOT_READY` forever; there is no "start over" action yet (a later settings task can add one, for example after repeated failures). (The last known limit, a transient Keystore failure marking the account as needing a sign-in, is fixed in the second round, item 6.)

## Second round (second security review)

Seven findings, plus one test problem found on CI. Everything is on `task/t11`. `FFI_API_VERSION` stays 4 (see item 6).

1. **High: on Android 8 to 11 a Keystore outage looked like key loss, and a new key could be made over the real one.** On keystore1 `aliases()` returns an empty set and `getKey` returns null when the service call fails, so three empty answers in 600 ms proved nothing, and `keyForSealing` could then `generate()` a new key, after which every secret read as corrupt. Now (`KeystoreKeySource.kt`, `AppSecrets.kt`, `LossConfirmation.kt`):
   - **A canary key.** `create()` makes `croft.wrapping.v1.canary` (a second, tiny key) before the wrapping key. The wrapping key is lost only if, on all three spaced checks, `getKey` is null, `aliases()` answers with a non-empty list that lacks it, and the canary is listed and does an encryption. An empty or failing `aliases()`, an alias that is listed but not returned, a canary that fails, or any mixed answer is `UNAVAILABLE`. A `KeyPermanentlyInvalidatedException` (or an API 33 key-specific error) is still definite at once.
   - **Weak evidence must persist.** `SecretBoxException` has a `weak` flag. It is set on API below 31 for the canary evidence, and on every API for "main key and canary both look absent" (an `UNAVAILABLE` that cannot be told from a wiped keystore). A weak answer is acted on only when it was seen at 3 app starts over at least one hour (`LossConfirmation`: first-seen time and count in `loss-suspected.v1`, one count per process; a start that opens the key normally deletes the file). Until then the open fails `NOT_READY` and nothing moves.
   - **A key is never made over wrapped files.** `keyForSealing` never creates a key; `WrappingKeySource.create()` does, and only `AppSecrets` calls it: on a true first run (no `db-key.v1`, no account secret, no database, no quarantine), or in the reset after a declared loss (definite evidence, or weak evidence that has persisted), when everything wrapped is already in the quarantine. A reset that stopped before the new key was written (quarantine present, nothing wrapped left) is finished by the next start; it is not taken for a first run. `requireNoWrappedFiles()` guards both calls, and `SecretStore.hasAny()` throws `IOException` when it cannot list the folder instead of answering "none".
   - Known limit: a keystore that was wiped completely while the app's data survived is declared lost only after the persistence rule (3 starts, one hour). A permanently empty answer from a broken keystore stays `NOT_READY`; there is still no "start over" action.
   - Tests: `KeystoreKeySourceTest` (`aMainKeyThatIsMissingWhileTheCanaryIsListedAndUsableIsLostOnThreeSpacedChecks`, `onApi30TheSameEvidenceIsWeak`, `anEmptyAliasListIsUnavailableNotALoss`, `aMissingCanaryMeansTheKeystoreIsNotAnsweringSoItIsUnavailable`, `aCanaryThatIsListedButDoesNotWorkIsUnavailable`, `oneCanaryFailureAmongTheChecksKeepsItFromBeingALoss`, `sealingNeverGeneratesAKeyWhateverTheKeystoreAnswers`, `createMakesTheCanaryAndThenTheMainKey`); `AppSecretsTest` (`aWeaklySuspectedLossIsActedOnOnlyAfterThreeStartsOverAnHour`, `threeStartsWithinAnHourAreNotEnoughAndAnHourWithTwoStartsIsNotEither`, `aStartThatOpensTheKeyForgetsTheSuspicion`, `theCountGoesUpOncePerProcessHoweverOftenTheKeyIsAsked`, `aKeyAndCanaryThatBothLookAbsentAreAlsoOnlyDeclaredLostWhenTheyPersist`, `aDefiniteLossIsNotHeldBackByThePersistenceRule`, `noWrappingKeyIsMadeWhileAnyWrappedFileExistsWhateverTheKeystoreSays`, `afterADeclaredLossTheNewKeyIsMadeByTheResetPathOnlyAndOnlyOnceTheLossIsConfirmed`).
2. **The quarantine was close to a delayed delete.** At the first `databaseKey()` of a process, before the core is opened, `AppSecrets` looks for the newest incident (not the one this start just made) whose `key/db-key.v1` opens with the current wrapping key: the loss was a false alarm. If nothing new was written since the reset (no account secret exists; the database is only ever filled once an account is signed in), it puts the database, secrets and key back by itself and clears `KeyLossNotice`. If there is new data it leaves it alone and sets `quarantineRestore.available` (a `StateFlow<Boolean>`); `quarantineRestore.restore()` (core closed, off the main thread) then swaps, and `dismiss()` hides the offer for good. The files that were live go to `<incident>/superseded/`, so even this is reversible. The swap writes a `restoring` marker first, moves the key last by one atomic rename, and a run that was cut short is finished at the next start. A start now counts for the quarantine's housekeeping (7 days and 3 starts) only after `Core.open` succeeded: `openCore` calls `AppSecrets.recordSuccessfulStart()` once the core is open; `databaseKey()` counts nothing. Tests: `AppSecretsTest` (`aWrongCallIsUndoneAtTheNextStartWhenNothingNewWasWritten`, `aWrongCallWithNewDataIsOfferedNotRestoredAndRestoresOnRequest`, `anOfferThePersonDismissesDoesNotComeBack`, `aRealLossIsNotRestored`, `aRestoreThatWasCutShortIsFinishedAtTheNextStart`, `obtainingTheKeyIsNotAStartUntilTheCoreHasOpened`), `OpenCoreTest.aStartCountsOnlyOnceTheCoreHasOpened`.
3. **Long waits under locks (ANR risk).** `databaseKey()` and `openCore` throw `IllegalStateException` on the main thread (`MainThreadCheck`, injectable; documented on both). `AccountSecrets.addPasswordAccount` and `removeAccount` run on `Dispatchers.IO` (a constructor parameter). The Keystore back-off sleeps outside the monitors: `KeystoreKeySource` synchronizes each single check and sleeps between them without the monitor; `SecretStore` seals and opens with no monitor held (only the file work is synchronized; a damaged entry is deleted only if it is still the bytes that were read); `AppSecrets.databaseKey()` runs one pass under its process lock and file lock, releases both, sleeps, and runs the next. Tests: `OpenCoreTest.openCoreRefusesTheMainThreadBeforeAnythingIsTouched`, `AppSecretsTest.theKeyIsRefusedOnTheMainThreadAndNothingIsTouched`, `AppSecretsTest.theRetryBackoffSleepsWithTheProcessLockReleased`, `SecretStoreTest.aWaitInsideTheBoxDoesNotHoldTheStoresMonitor`, `KeystoreKeySourceTest.theWaitsBetweenChecksHappenWithoutTheMonitorHeld`, `SecretStoreCredentialsTest.theCallersPasswordArrayIsLeftAloneAndAddRunsOffTheCallingThread`.
4. **The password copy was not wiped.** `AccountSecrets.addPasswordAccount` keeps the `password.copyOf()` it builds the credential from in a variable and `fill(0)`s it in `finally`. (The wipe of the copy is not observable from a test; `theCallersPasswordArrayIsLeftAloneAndAddRunsOffTheCallingThread` only checks that the caller's array is untouched.)
5. **An `IOException` while storing left an account without a secret.** It is caught like `SecretBoxException`: the secrets and the account are removed again and the exception is rethrown. Test: `SecretStoreCredentialsTest.ifTheSecretFileCannotBeWrittenTheAccountIsNotKeptEither` (a directory where the temporary file must go).
6. **A Keystore that could not answer marked the account "needs sign-in".** New fieldless `ProviderError::NotReady` (Rust `core/ffi/src/credentials.rs`); `ProviderError::Failed` keeps its meaning ("no credential"). `SecretStoreCredentials.credential` throws `ProviderException.NotReady` for `UNAVAILABLE` and for a weak (suspected) loss; a definite loss still reads as no credential. In the core, `NotReady` is a transient failure of that connection attempt: `AccountBackend` answers `BackendError::Transient`, the account is not paused, `sign_in_needed` is not called, and the backend asks the provider again on a later call after a back-off of 2 s, doubling to at most 5 min (the engine retries on its own schedule and on every poke such as `sync_now`). `signed_in` with a `NotReady` provider clears the needs-sign-in state and retries the same way. Tests: Rust `a_provider_that_is_not_ready_does_not_pause_the_account_and_is_asked_again` and `signed_in_with_a_provider_that_is_not_ready_is_not_a_missing_credential`; Kotlin `SecretStoreCredentialsTest.aKeystoreThatCannotAnswerIsNotReadyAndALostKeyReadsAsNoCredential` and `aKeystoreThatIsNotReadyAtOpenDoesNotMarkTheAccountAndTheCoreAsksAgain`. `FFI_API_VERSION` stays 4: version 4 has never been released (see T10, "As built").
7. **A bad `account.max_id` setting made every insert fail.** `core/storage/src/accounts.rs::insert` treats a setting that is not an integer (a JSON error) as absent, takes the id from `MAX(id)` and overwrites the setting; a database error still fails the insert. Test: `accounts::tests::a_mark_that_is_not_an_integer_is_ignored_and_overwritten`.
8. **Two tests failed on CI (Gradle) and passed locally.** `SecretStoreCredentialsTest.theCoreGetsTheStoredPasswordWhenItReopensAnAccount` and `aMissingSecretLeadsToNeedsSignInAndTheAccountIsMarked` failed only when the whole suite ran in one JVM. Cause: Robolectric loads the app's classes, including the generated `uniffi.croft_ffi` bindings, in its own class loader, so the JVM held two copies of the bindings, each with its own table of callback objects, over one native library. The library keeps one table of callback entry points; the copy that registered last (a Robolectric test that loads the library) received every callback with handles that only the other copy knew, and the log showed `UniffiHandleMap: Invalid handle`. The provider then looked like it had no credential. It depended on test order (it failed once a Robolectric test had run between two plain tests), which is why a single class or a plain JUnit run never showed it. Fix: `CroftRobolectricRunner` (in `src/test`) shares `uniffi.croft_ffi` and `com.sun.jna` with the parent loader (`doNotAcquirePackage`); the three Robolectric classes use it. Reproduced with `--tests CredentialPrintingTest --tests MainActivityTest --tests SecretStoreCredentialsTest`, fixed, and the whole suite passes. Not a timing problem, so no timeout was raised.
